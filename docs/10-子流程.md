# 06 · 子流程

> 📚 阅读顺序 **10/14** · ◀ 上一节 [09-运行时加签与协办](09-运行时加签与协办.md) · ▶ 下一节 [11-任务调度](11-任务调度.md) · [目录](README.md)

> `wfSubProcess` 节点把另一个已发布的流程定义作为一步执行。实现：`SubProcessNode` + `StartSubProcessHandler`。

## 基础示例

```json
{
  "id": "sub_pay",
  "type": "ingenious:wfSubProcess",
  "text": { "value": "支付子流程" },
  "properties": {
    "process_define_id": "wf-payment",
    "version": 1
  }
}
```

| 属性 | 必填 | 说明 |
|------|------|------|
| `process_define_id` | 是 | 子流程定义 id；缺省时回退用**节点名**查找 |
| `version` | 否 | 指定版本；缺省用最新发布版 |

## 执行链路

```
父实例推进到 wfSubProcess 节点
  → 按 process_define_id + version 取子定义（不存在抛 DefinitionException）
  → 以当前操作人 + 全量父变量启动子实例
  → 子实例 parentId = 父实例id，parentNodeName = 节点名
  → 父实例等待；子实例按自身流程独立推进
  → 子实例结束 → 父实例从该节点继续向后流转
```

## 父子关系与变量

| 维度 | 行为 |
|------|------|
| 关联 | 子实例 `parentId` 指回父实例，可按树查询层级 |
| 变量起点 | 子实例从父实例**全量复制**起步 |
| 变量隔离 | 启动后两侧变量相互独立，子流程变量不会回写父实例 |
| 嵌套深度 | 子流程内部可再放 decision/fork/会签，甚至再嵌套子流程（多层递归） |

## 典型场景

```text
采购主流程：start → 审批 → sub_pay(支付子流程) → 入账 → end
                                   └ 子流程内部：发起 → 三方对账(会签) → 金额判断 → 支付/驳回
```

主流程不关心支付细节，子流程可独立改版（version 沉淀历史），互不影响。

## 注意

- 子定义必须**已发布**（未发布/不存在抛 `DefinitionException`）
- 子流程没有"取消时联动取消父流程"的隐式行为，终止子实例需从父实例或监控页操作
- 需要子流程结果参与父流程判断时，在子流程**最后一步**把结果写到自身变量，父流程通过实例监控接口读取

## 多层嵌套查询

父子链通过 `parentId` 逐级上溯：

```
孙实例.parentId → 子实例.id
子实例.parentId → 父实例.id
父实例.parentId → null（顶层）
```

插件层实例监控页按 parentId 组装层级树展示；排查时按 `process_instance_id` + `parent_id` 两列即可还原整棵树。

## 设计建议

| 建议 | 原因 |
|------|------|
| 子流程职责单一 | 支付/合同/出差等独立域各自成流程，改版互不影响 |
| 用 version 而不是新建 id | 同一业务子流程升级走版本沉淀，历史实例仍指向旧版本 |
| 子流程变量命名加前缀 | 父变量全量复制进子实例，命名冲突会覆盖（如都用 `f_status`） |
| 深嵌套控制在 2 层内 | 排查与监控复杂度随层级上升明显 |

```php
// 启动含子流程节点的主流程，父变量全量进入子实例
$engine->startProcess('wf-purchase', '6', [
    'f_order_id' => 'PO20260914001',
    'f_amount'   => 88000,     // 子流程的决策/会签可直接引用
]);
```
